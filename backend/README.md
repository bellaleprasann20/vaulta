# Vaulta — Backend

FastAPI + SQLAlchemy + PostgreSQL (Supabase) backend for Vaulta, a
cloud-based media file storage and sharing service.

## Stack

- **Framework:** FastAPI
- **ORM:** SQLAlchemy 2.0
- **Database:** PostgreSQL (via Supabase, or any Postgres instance)
- **Migrations:** Alembic
- **Auth:** JWT (access + refresh tokens), bcrypt password hashing
- **Storage:** Supabase Storage or AWS S3 (signed upload/download URLs)

## Setup

**1. Create a virtual environment and install dependencies**

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
```

**2. Configure environment variables**

```bash
cp .env.example .env
```

Then edit `.env` and fill in:
- `SECRET_KEY` / `REFRESH_SECRET_KEY` — generate with:
  ```bash
  python -c "import secrets; print(secrets.token_urlsafe(64))"
  ```
- `DATABASE_URL` — your Supabase (or other Postgres) connection string
- `SUPABASE_URL` / `SUPABASE_KEY` / `SUPABASE_BUCKET` — if using Supabase Storage
  (or the `AWS_*` variables if `STORAGE_PROVIDER=s3`)

**3. Run database migrations**

```bash
alembic upgrade head
```

This creates all 8 tables (`users`, `folders`, `files`, `file_versions`,
`shares`, `link_shares`, `stars`, `activities`) plus their enums, indexes,
and constraints.

**4. Start the dev server**

```bash
uvicorn app.main:app --reload
```

The API is now running at `http://localhost:8000`. Interactive docs:
- Swagger UI: `http://localhost:8000/docs`
- ReDoc: `http://localhost:8000/redoc`

## Running tests

```bash
pytest
```

The test suite (55 tests across auth, files, folders, sharing, and search)
runs against an isolated in-memory SQLite database per test, with the
storage layer mocked — no real database or cloud credentials needed to
run `pytest`.

## Project structure

```
app/
├── core/       # config, database session, security (JWT/hashing), DI
├── models/     # SQLAlchemy ORM models
├── schemas/    # Pydantic request/response models
├── routes/     # API endpoints (one router per resource)
├── services/   # business logic — routes stay thin, services do the work
└── utils/      # validators, permission checks, file helpers, response envelopes
migrations/     # Alembic migrations
tests/          # pytest suite
```

## Creating a new migration

After changing a model in `app/models/`:

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

Always review the autogenerated file before applying it — Alembic is good
but not infallible, especially around constraint and enum changes.

## API overview

| Router | Base path | Covers |
|---|---|---|
| auth | `/api/v1/auth` | register, login, refresh, logout, me |
| users | `/api/v1/users` | profile, storage quota |
| files | `/api/v1/files` | upload lifecycle, CRUD, download, versions, star |
| folders | `/api/v1/folders` | create, contents/breadcrumbs, rename/move, delete |
| shares | `/api/v1/shares` | user-to-user sharing (viewer/editor roles) |
| public-links | `/api/v1/public-links` | shareable links, anonymous access |
| search | `/api/v1/search` | name/type search |
| stars | `/api/v1/stars` | starred items listing |
| trash | `/api/v1/trash` | list/restore/empty trash |

Full request/response schemas are available at `/docs` once the server
is running.
